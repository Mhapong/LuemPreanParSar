## 1. ปัญหาที่ต้องการแก้

คนไทยที่พิมพ์ทั้งภาษาไทยและอังกฤษเจอปัญหานี้ทุกวัน:

> ตั้งใจพิมพ์ "สวัสดี" แต่ลืมเปลี่ยนภาษา หน้าจอเลยขึ้นว่า `l;ylfu`

ผลคือต้องลบทิ้งทั้งหมด กดเปลี่ยนภาษา แล้วพิมพ์ใหม่ เสียเวลาและน่ารำคาญ บน Windows และ Mac มีโปรแกรมแก้ให้อัตโนมัติ เช่น RightLang และ Punto Switcher แต่บน Linux แทบไม่มี

**เป้าหมาย:** สร้างโปรแกรมบน Linux ที่**รู้เองว่าพิมพ์ผิดภาษา แล้วแก้ให้ทันที**

## 3. แนวคิดหลัก

### 3.1 ทำไมสร้างข้อมูลฝึกได้ฟรี

AI ต้องเรียนจากตัวอย่างที่มี "เฉลย" ปกติต้องจ้างคนมานั่งเขียนเฉลยทีละตัว แต่งานนี้ไม่ต้อง เพราะ**รู้อยู่แล้วว่าแต่ละปุ่มพิมพ์ตัวอะไร**ในแต่ละภาษา

```
เอาข้อความไทยจริง         "สวัสดี"
แปลงตามตำแหน่งปุ่ม  →     "l;ylfu"    ← นี่คือ "ตัวอย่างพิมพ์ผิดแป้น" พร้อมเฉลย
```

ทำแบบนี้กับบทความ Wikipedia หลายหมื่นบทความ ก็ได้ตัวอย่างหลายล้านตัวอย่างโดยไม่เสียแรงเลย

### 3.2 คำถามที่ AI ต้องตอบมีแค่ข้อเดียว

ตัวอักษรที่ขึ้นบนจอบอกอยู่แล้วว่าเครื่องตั้งภาษาอะไร (ขึ้นตัวไทยก็คือตั้งเป็นไทย) AI จึงต้องตอบแค่ว่า

> **"ผู้ใช้ตั้งใจพิมพ์ภาษานี้จริงไหม?"**

| หน้าจอขึ้นว่า | เครื่องตั้งเป็น | ผู้ใช้ตั้งใจพิมพ์ | คำตอบ |
|---|---|---|---|
| `สวัสดี` | ไทย | ไทย | ✅ ถูกแล้ว |
| `hello` | อังกฤษ | อังกฤษ | ✅ ถูกแล้ว |
| `l;ylfu` | อังกฤษ | ไทย | ❌ ผิดแป้น |
| `้ำสสน` | ไทย | อังกฤษ | ❌ ผิดแป้น |

AI ตอบเป็น**คะแนนความมั่นใจ** 0 ถึง 1 เช่น `l;ylfu` ได้ 0.99 แปลว่า "มั่นใจ 99% ว่าพิมพ์ผิดแป้น"

### 3.3 ตรวจ 2 จังหวะ

| จังหวะ | ตรวจเมื่อไร | ตัวอย่าง | แก้เมื่อมั่นใจ |
|---|---|---|---|
| **A. ระหว่างพิมพ์** | ทุกครั้งที่กดปุ่ม (หลังพิมพ์ไปสัก 2–3 ตัว) | เห็นแค่ `l;y` | **มากๆ** เช่น 99% |
| **B. ตอนกด space** | ตอนพิมพ์จบคำ | เห็นทั้งคำ `l;ylfu` | น้อยลงได้ เช่น 95% |

**ทำไมต้อง 2 จังหวะ:** จังหวะ A แก้เร็ว ผู้ใช้เห็นข้อความผิดแค่แป๊บเดียว แต่ข้อมูลยังน้อยจึงต้องระวังมาก ส่วนจังหวะ B เห็นคำเต็มแล้ว แม่นกว่า จึงใช้เก็บกรณีที่จังหวะ A ไม่กล้าแก้

**ทางสำรอง:** มีปุ่มลัด (เช่น Pause) ให้ผู้ใช้สั่งแก้คำล่าสุดเองได้ทันที โดยไม่ต้องรอ AI

<details>
<summary>รายละเอียดทางเทคนิค</summary>

- Input: ข้อความตั้งแต่ขอบเขตล่าสุด (space, Enter, คลิก) ไม่เกิน 32 ตัวอักษร
- Output: `P(wrong | typed_text)`
- จังหวะ A แก้เมื่อ `P ≥ τ_type` และ `len ≥ k_min`; จังหวะ B แก้เมื่อ `P ≥ τ_space`
- เลือก `τ_type`, `τ_space`, `k_min` จาก validation set โดยตั้งเป้า precision ≥ 99%
- เป็น binary classification ซึ่งเทียบเท่ากับ 4 คลาส (th_ok, en_ok, th_as_en, en_as_th) แต่วัดผลง่ายกว่า

</details>

## 4. ข้อมูลฝึก (Dataset)

### 4.1 เอาข้อความมาจากไหน

| แหล่ง | ทำไมเลือก |
|---|---|
| **Wikipedia ภาษาไทย** (20,000 บทความ) | มีคำศัพท์ไทยหลากหลาย |
| **Wisesight** (ข้อความโซเชียล 26,703 ข้อความ) | เป็นภาษาพูดแบบที่คนพิมพ์แชทจริง มีคำย่อ คำสะกดไม่เป็นทางการ และอังกฤษปน |
| **Wikipedia ภาษาอังกฤษ** (20,000 บทความ) | ฝั่งภาษาอังกฤษ |
| **ศัพท์คอมพิวเตอร์** | คำสั่งอย่าง `git` `sudo` ชื่อโปรแกรม ชื่อตัวแปร เพราะโปรแกรมเมอร์พิมพ์คำพวกนี้บ่อย และดูแปลกจนอาจถูกแก้ผิด |

**ข้อห้าม:** ห้ามใช้ประวัติคำสั่งส่วนตัวในเครื่อง เพราะอาจมีรหัสผ่านติดไปด้วย

### 4.2 ขั้นตอนเตรียมข้อมูล

1. **ทำความสะอาด:** ตัดตัวอักษรที่พิมพ์จากคีย์บอร์ดไม่ได้ทิ้ง (เช่น emoji) และตัดข้อความซ้ำ
2. **แบ่งข้อมูลเป็น 3 ส่วน** (เหมือนแบบฝึกหัด / ข้อสอบย่อย / ข้อสอบจริง) **โดยแบ่งตามบทความ** ประโยคจากบทความเดียวกันต้องอยู่ส่วนเดียวกัน ไม่อย่างนั้นจะเหมือนข้อสอบรั่ว คะแนนจะสูงเกินจริง
3. **ตัดเป็นช่วงสั้น** ยาวไม่เกิน 32 ตัวอักษร ให้เท่ากับสิ่งที่ผู้ใช้พิมพ์ในแต่ละคำ
4. **สร้างตัวอย่าง 2 แบบจากแต่ละช่วง:** แบบเดิม (เฉลย "ถูก") กับแบบแปลงแป้น (เฉลย "ผิด")
5. **เพิ่มตัวอย่างหลอก** (hard negative): ข้อความที่พิมพ์ถูกแต่ดูแปลก เช่น รหัสผ่าน `xK9!q2`, เว็บไซต์, คำสั่ง `git`, คำย่อ `ok` เพื่อสอน AI ว่า "แปลกไม่ได้แปลว่าผิด"
6. **จัดสัดส่วน** ให้ตัวอย่าง "ถูก" กับ "ผิด" มีอย่างละครึ่ง

**เก็บเป็นคำเต็ม ไม่เก็บทุกส่วนต้นของคำ:** ตอนฝึก โปรแกรมจะสุ่มตัดคำให้สั้นยาวต่างกันเองทุกรอบ (เช่น `l;ylfu` → `l;y`) ไฟล์จึงเล็กลงหลายเท่า และ AI ได้เห็นตัวอย่างหลากหลายขึ้น

<details>
<summary>รายละเอียดทางเทคนิค</summary>

- Normalize Unicode NFC; แบ่ง train/val/test 80/10/10 ตาม document id; seed ตายตัว (42)
- ตัวอย่าง `wrong` สร้างด้วย `th_to_en` / `en_to_th` จาก [src/luem/layout.py](../src/luem/layout.py)
- CNN: DataLoader สุ่ม prefix ทุก epoch (data augmentation); GRU: ใช้ output ทุก timestep; `evaluate.py` สร้าง prefix 1..n เองตอนวัด chars-to-detect
- ไฟล์ output `data/processed/{train,val,test}.jsonl` ขนาดเป้าหมาย 1–2 ล้านตัวอย่าง

```json
{"text": "l;ylfu", "active": "en", "label": "wrong", "intended": "สวัสดี", "source": "wisesight", "kind": "normal"}
```

`kind` = `normal` หรือ `hard_negative` ใช้แยกรายงานผล

</details>

## 5. AI ที่จะเปรียบเทียบ

ทำ 3 แบบ จากง่ายไปยาก เพื่อตอบว่า "วิธีที่ซับซ้อนกว่า ดีกว่าจริงไหม"

| # | วิธี | ทำงานอย่างไร (แบบง่าย) | คาดว่า |
|---|---|---|---|
| 1 | **เปิดพจนานุกรม** | แปลงข้อความแล้วดูว่าเป็นคำที่มีอยู่จริงไหม | ง่าย แต่แพ้คำที่ยังพิมพ์ไม่จบ และคำที่ไม่อยู่ในพจนานุกรม |
| 2 | **สถิติกลุ่มตัวอักษร** (n-gram) | นับว่ากลุ่มตัวอักษรไหนเจอบ่อยในแต่ละภาษา เช่น `the` พบบ่อยในภาษาอังกฤษ ส่วน `l;y` ไม่เคยพบเลย | เร็วมาก เป็นคู่เทียบที่แข็งแรง |
| 3 | **CNN** (โมเดลหลัก) | neural network ที่ "ส่องหา" รูปแบบสั้นๆ ในข้อความ เหมือนใช้แว่นขยายกวาดไปทีละช่วง | แม่นที่สุด และเรียนรู้จากตัวอย่างหลอกได้ |
| 3b | **GRU** (ถ้ามีเวลา) | neural network ที่อ่านทีละตัวเหมือนคนอ่านหนังสือ | ใช้เปรียบเทียบกับ CNN ในรายงาน |

**ทำไมเลือก CNN เป็นตัวหลัก:** สิ่งที่บอกว่าพิมพ์ผิดแป้นคือกลุ่มตัวอักษรสั้นๆ ที่ไม่มีในภาษาจริง เช่น `l;y` หรือ `้ำ` CNN ถนัดหารูปแบบสั้นแบบนี้ที่สุด และเร็วมาก ใช้เวลาไม่ถึง 1 มิลลิวินาที ขณะที่คนกดแต่ละปุ่มห่างกันประมาณ 100 มิลลิวินาที จึงตอบทันก่อนผู้ใช้กดปุ่มถัดไปเสมอ

<details>
<summary>รายละเอียดทางเทคนิค</summary>

| # | รายละเอียด |
|---|---|
| 1 | Dictionary: ตัดคำไทยด้วย `pythainlp` |
| 2 | Char n-gram LM: n=5, Kneser-Ney หรือ stupid backoff แยกภาษาละตัว เปรียบเทียบ `log P_th(x_as_th) − log P_en(x_as_en)` |
| 3 | Char-CNN: Embedding (~190 ตัวอักษร × 32 มิติ) → Conv1D kernel 2–5 → max-pool → linear → sigmoid, < 200k parameters, export ONNX |
| 3b | GRU: embedding 32, hidden 128, per-timestep loss |

ทุกโมเดลใช้ interface เดียวกัน `predict(text) -> float` เพื่อให้วัดผลและ demo สลับโมเดลได้

</details>

## 6. วัดผลอย่างไร

| วัดอะไร | หมายความว่า | ทำไมสำคัญ |
|---|---|---|
| **แก้ถูกกี่ %** (precision) | ทุกครั้งที่โปรแกรมแก้ แก้ถูกกี่ครั้ง | **สำคัญที่สุด** เพราะการแก้ทั้งที่ผู้ใช้พิมพ์ถูก น่ารำคาญกว่าไม่มีโปรแกรมเลย |
| **จับได้กี่ %** (recall) | ที่พิมพ์ผิดจริง โปรแกรมจับได้กี่ครั้ง | |
| **แก้ผิดกับตัวอย่างหลอกกี่ %** | รหัสผ่าน, `git` และอื่นๆ ถูกแก้ผิดบ่อยแค่ไหน | ดูว่า AI ถูกหลอกง่ายไหม |
| **ต้องพิมพ์กี่ตัวถึงรู้** (chars-to-detect) | เช่น พิมพ์ `l;y` (3 ตัว) แล้วรู้ทันที | **ตัวเลขหลักของงาน** ยิ่งน้อย ผู้ใช้ยิ่งต้องลบน้อย |
| **แก้ได้ในจังหวะไหน** | % ที่แก้ระหว่างพิมพ์, % ที่แก้ตอนกด space, % ที่ไม่ถูกแก้ | ดูว่าการตรวจ 2 จังหวะคุ้มไหม |
| **เร็วแค่ไหน** (latency) | ใช้เวลากี่มิลลิวินาทีต่อการกด 1 ครั้ง | ต้องไม่ถึง 5 ms ผู้ใช้จึงไม่รู้สึกว่าช้า |
| **ไฟล์ใหญ่แค่ไหน** | ขนาดไฟล์ AI | ดูว่าใช้งานจริงได้ไหม |

นอกจากนี้จะ**ดูตัวอย่างที่ AI ทำผิด 50 ตัวอย่าง** แล้วจัดกลุ่มว่าผิดเพราะอะไร เช่น คำสั้นเกินไป คำย่อ หรือชื่อเฉพาะ

## 7. โปรแกรมสาธิตบน Linux

### 7.1 ทำงานอย่างไร

```
1. ฟังว่าผู้ใช้กดปุ่มอะไร           (ได้หมายเลขปุ่ม เช่น 38, 39, 21)
2. แปลงหมายเลขปุ่มเป็นตัวอักษร      (ตามภาษาที่ตั้งอยู่: l ; y)
3. ถาม AI ว่าพิมพ์ผิดแป้นไหม        (ได้คะแนน 0.99)
4. ถ้ามั่นใจ:
     - กดลบ 3 ครั้ง
     - กด Super+Space เปลี่ยนภาษา
     - กดปุ่มหมายเลขเดิมซ้ำ (38, 39, 21)  → คราวนี้ได้ "สวั"
5. ผู้ใช้พิมพ์ต่อในภาษาที่ถูกแล้ว      → "สวัสดี"
```

**จุดที่ทำให้ง่าย:** หลังเปลี่ยนภาษาแล้ว แค่กด**ปุ่มเดิมซ้ำ** ระบบก็แปลงเป็นตัวอักษรภาษาใหม่ให้เอง ไม่ต้องคำนวณเองว่าต้องพิมพ์ตัวอะไร

### 7.2 ทำไมทำงานในระดับลึกของระบบ

เครื่องที่ใช้คือ **Linux Mint** ซึ่งเลือกระบบหน้าจอได้ 2 แบบ

- **X11:** แบบเก่า โปรแกรมแอบดูการพิมพ์ของโปรแกรมอื่นได้ง่าย
- **Wayland:** แบบใหม่ที่จะใช้ **ห้ามโปรแกรมแอบดูกัน** เพื่อความปลอดภัย

เพราะ Wayland ห้ามแอบดู จึงต้องไปฟังที่ระดับลึกกว่า คือฟังจากคีย์บอร์ดโดยตรง (evdev) และพิมพ์ผ่านคีย์บอร์ดปลอม (uinput) **ข้อดีที่ได้มาด้วย:** วิธีนี้ใช้ได้กับทั้ง X11 และ Wayland ถ้า Wayland มีปัญหาตอน demo ก็สลับไปใช้ X11 ได้ทันที

### 7.3 ผลการทดลองล่วงหน้า (1 ต.ค.)

ก่อนลงมือทำจริง ได้ทดลองสั้นๆ ว่าวิธีนี้ทำได้ไหม

| ทดลอง | ผล |
|---|---|
| ฟังได้ไหมว่ากดปุ่มอะไร | ✅ ได้ ทั้งภาษาไทยและอังกฤษ รวมถึงตอนกด Shift |
| ลบและพิมพ์ใหม่ผ่านคีย์บอร์ดปลอมได้ไหม | ✅ ได้ |
| อ่านค่าภาษาปัจจุบันจากค่าตั้งของระบบได้ไหม | ❌ **ไม่ได้** ค่าที่อ่านได้ไม่ตรงกับความจริง |
| เปลี่ยนภาษาผ่านค่าตั้งของระบบได้ไหม | ❌ **ไม่ได้** |
| เปลี่ยนภาษาด้วยการกด Super+Space ผ่านคีย์บอร์ดปลอมได้ไหม | ✅ ได้ |

**สิ่งที่ต้องทำต่อจากผลนี้:** โปรแกรมต้อง**จำเองว่าตอนนี้เป็นภาษาอะไร** โดยนับว่ามีการกด Super+Space ไปกี่ครั้ง

**ข้อจำกัด:** ถ้าผู้ใช้เปลี่ยนภาษาด้วยการคลิกปุ่มภาษาบนแถบงาน โปรแกรมจะไม่รู้ จึงต้องมีปุ่มลัดให้รีเซ็ตสถานะ

### 7.4 ความปลอดภัยและความสะดวก

- **ต้องขออนุญาตฟังคีย์บอร์ด** (เพิ่มผู้ใช้เข้ากลุ่ม `input`) ข้อแลกเปลี่ยนคือ ผู้ที่อยู่ในกลุ่มนี้ฟังการพิมพ์ทั้งหมดในเครื่องได้ จึงต้องเขียนไว้ในรายงาน
- **ไม่บันทึกสิ่งที่พิมพ์ลงไฟล์เด็ดขาด**
- มีปุ่มลัดเปิด/ปิดโปรแกรม
- **ลืมคำปัจจุบันทันที** เมื่อคลิกเมาส์ กด Enter กดลูกศร หรือใช้ปุ่มลัดอื่น เพราะเคอร์เซอร์อาจย้ายไปที่อื่นแล้ว ถ้าลบตอนนั้นจะลบผิดที่

<details>
<summary>รายละเอียดทางเทคนิค</summary>

- เครื่อง: Linux Mint 22.3, Cinnamon 6.6.9, layout `us,th,us`, มี IBus ทำงานอยู่
- ตั้งสิทธิ์ (ทำครั้งเดียว แล้ว logout/login):

```fish
sudo usermod -aG input $USER
echo 'KERNEL=="uinput", GROUP="input", MODE="0660"' | sudo tee /etc/udev/rules.d/99-uinput.rules
sudo udevadm control --reload-rules; and sudo udevadm trigger
```

- ผล spike: `gsettings org.cinnamon.desktop.input-sources current` ไม่ตามและไม่ควบคุม layout จริง; Super+Space ผ่าน uinput สลับได้
- ตอนเริ่ม daemon สมมติว่าเป็น `en`; กรอง event จากอุปกรณ์ uinput ของตัวเองกันวนลูป
- จังหวะ B: แอปได้รับ space ไปแล้ว ต้องลบ (ความยาวคำ + 1) แล้วพิมพ์ space คืน
- ไม่มี blacklist ตามหน้าต่าง เพราะ Wayland ไม่บอกว่าหน้าต่างไหนกำลังใช้งาน

</details>
